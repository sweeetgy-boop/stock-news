# stock-news

코스피+코스닥 전종목(약 2,800개)을 매일 저녁 스캔해 추천 10선을 텔레그램으로
보내고, 매일의 점수 스냅샷을 쌓아 금요일에 주간 분석을 발송한다.

## 구성

투 트랙 스크리너. 두 로직은 방향이 반대이므로 점수를 합산하지 않고 분리 운영한다.

- **트랙 V (매집, 역추세)** — 신용 강제청산 밴드 + 1년 고점 피보나치 되돌림
- **트랙 T (확증, 순추세)** — 20/40/60일 이동평균 골든크로스
- **시퀀스 결합** — 청산 밴드 진입 후 20거래일 내 골든크로스 = `S+` 등급

```
stocknews/
  config.py      파라미터 (-30%, 0.618, 20/40/60 전부 여기서 조정)
  contracts.py   스캐너 <-> 봇 결합점 (frozen dataclass)
  indicators.py  20/40/60 골든크로스 판정
  fibonacci.py   1년 고점 피보나치 되돌림 + '레벨 이하' 판정
  cost_basis.py  개미 평균단가 P0 추정 (A/B/C 폴백)
  liquidation.py 청산 밴드 + 청산압력점수(LPS)
  screener.py    투 트랙 통합 · 등급 판정
  store.py       SQLite 저장소 (시세 캐시 + 일별 점수 스냅샷 + 추천 이력)
  universe.py    전종목 목록 · 배제 필터 · 시세 적재
  daily.py       저녁 전종목 스캔 → 추천 10선 (슬롯 배정 + 섹터 분산)
  weekly.py      금요일 누적 분석 (자기검증 · 모멘텀 · 연속등재 · ETA)
  news_sources.py 뉴스 수집 (네이버금융 · Google News RSS · Yahoo · DART)
  news.py        뉴스 정리 (중복제거 · 사건 클러스터 · 종목태깅 · 중요도)
  exits.py       청산 규칙 엔진 (8계층 우선순위)
  flags.py       배제 플래그 공급원 (FDR 관리종목 · DART · 로컬 · 수동)
  renderer.py    텔레그램 조판 (표 미사용)
  ...
smoke_test.py    스모크 테스트 91건 (네트워크·실DB 미사용)
verify_env.py    requirements.txt 핀 대조 + 런타임 기능 점검
  notify.py      4중 게이트 + 발송
  data.py        pykrx / FinanceDataReader 로더
run_screen.py    실행부
```

## 설치

```bash
python -m venv venv
venv\Scripts\activate          # Windows
pip install -r requirements.txt
```

검증 환경: Python 3.12.10 / Windows. `requirements.txt` 34개 핀 전부 일치
확인됨 (`pip check` → No broken requirements found).

올라오므로 반드시 `-r requirements.txt` 를 쓰십시오.

## 스모크 테스트

네트워크와 실제 DB 없이 전 모듈을 합성 데이터로 태운다. 코드를 만진 뒤
반드시 먼저 돌리십시오.

```bash
python smoke_test.py        # 100개 검사
python smoke_test.py -v     # 실패 시 트레이스백까지
```

하나 실패해도 멈추지 않고 끝까지 돌린 뒤 한꺼번에 보고한다. 손으로 검산
가능한 앵커를 박아두어 파라미터를 흔들 때 회귀를 잡을 수 있다.

```
피보나치 : 고점 705,000 / 파동시작 300,000 -> 0.618 선 = 454,710
청산밴드 : P0 x 1.40 x 0.50 = 0.70 x P0 (-30%)
밴드위치 : -30% 지점의 정규화 위치 r = 0.50 (정중앙)
```

주요 회귀 방어 검사

```
스윙 저점이 '고점 이전' 구간에서 잡히는지 (섞으면 신호가 늦어진다)
이평 교차가 붙어서 진동할 때 신호가 반복 발생하지 않는지
청산 계층 0 이 이익 중에도 최우선인지
밴드 1일 이탈로는 손절이 발동하지 않는지 (꼬리 방어)
목표 익절이 중복 집행되지 않는지 (exits_done 비트)
청산 신호만으로 잔량이 줄지 않는지 (신호/체결 분리)
capital_impair 전용 TTL 이 로컬 갱신에 덮이지 않는지
플래그가 실제로 scan_all 로 흘러가 배제를 일으키는지
'현대차증권' 기사에 '현대차'가 오태깅되지 않는지
```

## 최초 구축 (한 번만)

```bash
python run_screen.py --mode master      # 전종목 마스터 + 업종 (2~3분)
python run_screen.py --mode backfill    # 히스토리 적재 (20~40분)
python run_screen.py --mode flags       # 배제 플래그 초기 구축
```

수동 플래그를 쓰려면 템플릿을 복사하십시오.

```bash
copy data\flags_manual.csv.example data\flags_manual.csv
```

`backfill`은 종목별로 체크포인트를 남긴다. 중간에 끊기면 같은 명령을 다시
실행하면 남은 종목만 이어서 받는다.

## 일상 운용

```bash
python run_screen.py --mode update          # 당일 시세 증분 (요청 2회, 수초)
python run_screen.py --mode credit          # 수동 신용잔고 주입 (주 1회면 충분)
python run_screen.py --mode export          # 전종목 점수표 CSV (협업용)
python run_screen.py --mode daily           # 전종목 스캔 + 추천 10선
python run_screen.py --mode weekly          # 금요일 주간 누적 분석
python run_screen.py --mode fib             # 피보 0.618 이하 목록
python run_screen.py --mode flash           # 아침 즉시 속보

python run_screen.py --mode news            # 뉴스 수집·정리만 (발송 없음)
python run_screen.py --mode brief-morning   # 아침 브리핑 (개장 전)
python run_screen.py --mode brief-evening   # 저녁 뉴스 정리
python run_screen.py --mode brief-weekly    # 주간 뉴스 테마 부침
```

포지션 / 청산

```bash
# 진입 (진입 시점 밴드·피보 레벨이 스냅샷으로 고정된다)
python run_screen.py --mode pos-open --ticker 329180 --qty 100 --price 455500

python run_screen.py --mode pos-list        # 보유 현황 + 미체결 청산 신호
python run_screen.py --mode exits           # 청산 판정 + 발송 (매일)

# 다음날 실제 체결 후 반영 (여기서만 잔량이 줄어든다)
python run_screen.py --mode fill --log-id 3 --fill-price 452000

python run_screen.py --mode pos-close --id 1   # 수동 종료
```

모든 모드에 `--dry-run`을 붙이면 텔레그램 대신 콘솔로 출력한다.
`--limit 50`으로 소수 종목만 돌려 먼저 확인하는 것을 권한다.

0   18  * * 1-5  ... run_screen.py --mode daily

## 데이터 흐름

```
[1회] master  →  tickers 테이블 (활성 종목 + 업종 + 시총)
[1회] backfill→  prices 테이블 (종목 × 420봉)
[매일] update →  prices 에 하루치 추가 ('일자별 전종목' 요청 2회)
[매일] daily  →  prices 읽어 전종목 채점
                 ├─ scans  테이블에 전종목 점수 스냅샷 저장
                 ├─ recos  테이블에 추천 10선 저장
                 └─ 텔레그램 발송
[금요일] weekly→ scans + recos + prices 를 교차 분석해 리포트 발송
```

`daily`는 네트워크를 쓰지 않는다. SQLite 읽기와 pandas 연산만 하므로
전종목 채점이 수 분 안에 끝난다.

뉴스는 별도 파이프라인이다.

```
[하루 2~3회] news → 수집 → 정규화 → 사건 클러스터 → 종목태깅 → 중요도
                  └─ news / news_tickers 테이블
[08:30] brief-morning  밤사이 해외 + 매크로 + 내 종목 + 주요 공시
[18:20] brief-evening  국내 공시·수급·테마·시황 + 추천 10선 교차
[금 18:40] brief-weekly 이번 주 vs 지난 주 테마 건수 변화
```

## 뉴스 정리 방식

뉴스에는 점수를 매기지 않는다. 호재/악재 판정은 기계가 하지 않는다.
이 모듈이 하는 일은 정리뿐이다.

```
① 정규화   제목에서 매체 꼬리표 · 대괄호 태그 · [단독][종합] 제거
② 중복제거 정규화 제목 + 매체 해시로 같은 기사를 합침
③ 클러스터 토큰 자카드 0.55 이상이면 같은 사건으로 묶음
④ 종목매핑 제목에서 유니버스 종목명 검색 (긴 이름 우선, 우선주 제외)
⑤ 분류     키워드 룰 13개 카테고리 (공시/수급/실적/매크로/반도체/…)
⑥ 중요도   매체 수 + 내 종목 여부 + 키워드 강도 + 신선도
```

중요도 설계에서 **1순위 신호는 헤드라인의 자극성이 아니라 '몇 개 매체가
같은 사건을 다뤘는가'**다. 단독 기사는 낮게, 여러 매체가 붙은 사건은 높게
본다. 여기에 보유·추천 종목 여부를 얹어 읽어야 할 순서를 만든다.

2글자 종목명은 일반 단어와 충돌해 오탐이 심하므로 화이트리스트만 허용하고,
`미래`·`한국`·`삼성` 같은 모호한 이름은 문맥 없이 매칭하지 않는다.

영문 해외 기사는 번역하지 않고 원문 제목 그대로 둔다. LLM 요약을 붙이려면
`process_and_store(store, raw, summarize_hook=...)`에 훅을 주입하면 된다.

## 추천 10선 선정 규칙

단순 점수 상위 10개가 아니다. 슬롯을 나눈다.

```
슬롯 1~2   시퀀스 확증 (S+) 최우선
슬롯 3~7   트랙 V 상위 (매집)
슬롯 8~10  트랙 T 상위 (확증)
빈 슬롯    전체 점수 순 보충
제약       동일 업종 최대 2개 / 20일 평균 거래대금 5억 이상
배제       스팩 · 우선주 · 리츠 · ETF/ETN · 관리종목
```

## 주간 리포트 7개 항목

```
① 자기검증     지난 추천의 실제 성적 vs 시장 중위 수익률  ← 맨 앞에 둔다
② 점수 모멘텀  5일간 매집점수 상승폭 상위
③ 연속 등재    반복 등재 종목 (하루짜리 노이즈 제거)
④ 신규/이탈    이번 주 진입 · 이탈 종목
⑤ 청산선 ETA   밴드 접근 속도로 -30% 도달 예상 거래일
⑥ 주중 이벤트  피보 0.618 하향 이탈 · 골든크로스 발생
⑦ 업종 분포    한 업종 40% 초과 시 편중 경고
```

①이 맨 앞인 이유는 검증 없는 추천은 시간이 지나면 반드시 신뢰를 잃기
때문이다. 초과수익이 0 이하로 나오면 리포트가 스스로 경고를 띄운다.

## 배제 플래그

청산 계층 0(무효화)과 진입 배제 필터가 같은 데이터를 쓴다. 공급원은 4단이다.

```
① FDR    관리종목        StockListing('KRX-ADMINISTRATIVE')
② DART   자본잠식률      fnlttSinglAcnt.json 의 자본금 vs 자본총계
         대규모 증자·CB   list.json 공시 제목 스캔 (최근 60일)
         감사의견        list.json 제목의 의견거절·한정 키워드
③ 로컬   거래정지 흔적   시장 거래일 대비 누락일 3일 이상
         동전주 위험     종가 1,000원 미만 30거래일 연속
         시세 불연속     전일 대비 -45% 이상 (액면분할·감자 흔적)
④ 수동   data/flags_manual.csv (항상 마지막에 덮어씀)
```

자본잠식률 계산은 별도(개별)재무제표를 우선한다. 거래소 관리종목 지정 기준이
개별 기준이기 때문이다. OFS가 없으면 CFS로 폴백한다.

```
자본잠식률 = (자본금 - 자본총계) / 자본금 x 100
자본총계 <= 0 이면 완전자본잠식(100%)
```

### 공급원이 실패하면 그 필드를 건드리지 않는다

갱신 전에 필드를 NULL로 비우는 이유는 **관리종목 해제를 반영**하기 위함이다.
비우지 않으면 한 번 켜진 플래그가 영구히 남아 정상화된 종목이 계속 배제된다.

그런데 조회가 실패했을 때도 비우면 멀쩡한 데이터를 날린다. 그래서 공급원이
성공했을 때만 해당 필드를 초기화한다. 실패하면 이전 값을 유지하고 경고만
남긴다. FDR 조회가 0건을 반환하는 경우도 실패로 취급한다. 관리종목이 0건인
시장은 현실적으로 없으므로 스키마 변경으로 본다.

### DART 호출량 관리

2,800종목 x 최대 8회 조회는 DART 일일 한도를 압박한다. 재무는 분기 단위로만
바뀌므로 30일 TTL 캐시를 두고, TTL이 지난 종목만 조회한다.

```bash
python run_screen.py --mode flags                    # 전체
python run_screen.py --mode flags --dart-limit 300   # 하루 300종목씩 분할
python run_screen.py --mode flags --no-dart          # 키 없이 FDR+로컬만
```

`corpCode.xml`(종목코드 → DART corp_code 매핑)은 `data/dart_corp_codes.json`에
7일 캐시된다.

### 동전주 배제의 근거

2026년 상장폐지 규정이 강화되어 1,000원 미만이 30거래일 이어지면 관리종목
지정 사유가 된다. 지정을 기다리지 않고 로컬 시세만으로 선제 배제한다. 외부
데이터가 필요 없어 항상 동작하는 유일한 배제 축이다.

### 시세 불연속은 배제가 아니라 재적재 신호

액면분할이 나면 캐시된 과거 봉과 신규 봉이 어긋나 1년 고점이 통째로 틀어지고
피보나치와 청산 밴드가 전부 엉뚱한 값이 된다. `flags` 모드가 의심 종목을
출력하니 해당 종목만 지우고 다시 받아야 한다.

```sql
DELETE FROM prices WHERE ticker='123456';
```
이후 `backfill_state`에서도 제거하고 `--mode backfill` 재실행.

## 청산 규칙

핵심 원칙은 **청산이 진입 근거를 거울처럼 따라간다**는 것이다. 진입이 두
트랙이면 청산도 두 갈래여야 한다. 하나의 청산 룰을 두 트랙에 공통 적용하는
것이 가장 흔하고 비싼 실수다.

```
트랙 V (매집·역추세)  밴드로 들어가서 밴드로 나온다
트랙 T (확증·순추세)  크로스로 들어가서 트레일링으로 나온다
공통                  +15% 절반 기계적 익절만 동일
```

우선순위(작을수록 우선). 같은 날 여러 개가 걸리면 **포지션당 하나만** 집행한다.

```
0 무효화    관리종목·감사의견·자본잠식·대규모증자·거래정지 → 손익 무관 전량
1 손절      V: 밴드 하단(-44%) 종가 3일 연속 이탈
            V: 밴드 밖 진입은 고정 -10% 또는 ATR×2 중 느슨한 쪽
            T: MA60 종가 2일 연속 하회 / 데드크로스 / 크로스봉 저가 -3%
2 트레일링  T: 최고 종가 대비 -8% 또는 MA20 이탈 (진입가 돌파 후 활성)
3 목표3차   V: 밴드 상단(-16%) 회복 → 잔량 전량 (진입 근거 소멸)
4 목표2차   V: 피보 0.382 회복 → 30%
5 목표1차   공통: +15% → 50% (교리 규칙 02)
6 시간      V: 15거래일 & 수익 <+3% / T: 20거래일 & MA20 하회
            공통: 신용잔고율 진입 대비 +1.5%p 재급증
7 순환매    보유 종목 간 당일 편차 15% 이상 → 급등 자산 50% 현금화
            편차 5% 미만이면 순환매 보류 (교리 규칙 01·03)
```

### 구현에서 지킨 세 가지

**진입 스냅샷 고정.** `positions` 테이블에 진입 시점의 `entry_band_lo/mid/hi`,
`entry_fib_0382/0618`, `entry_cross_low`를 저장하고 이후 절대 재계산하지 않는다.
매일 P0를 다시 구하면 주가 하락에 맞춰 손절선도 내려가 손절이 영원히
발동하지 않는다. 계좌를 녹이는 전형적인 방식이다.

**신호와 체결의 분리.** 종가로 판정하므로 실제 체결은 익일이다. `exits`는
`exit_log`에 `executed=0`으로 신호만 남기고, 잔량은 `--mode fill`로 실제
체결가를 넣을 때만 줄어든다. 신호만으로 잔량을 깎으면 팔지도 않은 물량을
팔았다고 착각한다.

목표 익절(계층 4·5)만 `exits_done` 비트를 세워 재발송을 막는다. 손절·트레일링·
시간 청산은 비트를 세우지 않는다. 포지션이 닫힐 때까지 매일 다시 알려야 한다.

**파생 상태는 매번 재계산.** `peak_close`, 밴드/MA 연속 이탈 일수를 DB 카운터로
증감시키지 않고 진입 이후 구간에서 다시 계산한다. 배치가 하루 빠지거나 두 번
돌아도 결과가 같아야 한다(멱등성).

### 알림 정책

청산은 진입 알림 예산 밖에서 나간다. 계층 0~1(무효화·손절)은 시간창을
무시하고 단건으로 즉시 발송하고, 나머지는 요약 1건으로 묶는다. 진입은
하루 늦어도 되지만 청산은 아니다.

## 4대 감시 시간대

창마다 목적이 다르므로 **트랙과 예산을 따로 준다.** 전역 예산 하나만 쓰면
09시에 소진해 정작 최우선 창인 10시가 무음이 된다.

```
09:00~09:35  반대매매    매집(V)·시퀀스만   예산 2   D+2 하한가 투매 진행 중
10:00~10:25  방향확정    전 트랙 허용       예산 3   ★ 최우선 · 휩쏘 종료 후
14:00~14:25  오후눌림    매집(V)·시퀀스만   예산 2   실망매물 스위칭 준비
15:20~15:35  종가확정    전 트랙 허용       예산 2   오버나이트 판단
```

**09시와 10시를 나눈 이유가 핵심이다.** 09:00은 반대매매가 동시호가에
하한가로 집행되는 순간이므로 투매를 '진행 중에' 잡아야 한다. 그래서 역추세
매집 트랙만 본다. 10시는 휩쏘가 걷히고 외국인·기관 알고리즘의 당일 방향이
확정된 뒤라 순추세 확증 트랙이 의미를 갖는다. 09시에 추세를 쫓으면 속임수
변동성에 걸린다.

시각 판정은 KST 고정이다(`notify.now_kst()`). 호스트 타임존이 UTC 여도
국내장 기준으로 동작한다.

## 신용잔고 실측 주입

이 시스템의 핵심 가설은 신용 강제청산이다. 그런데 종목별 신용잔고 실측을
자동으로 확보하지 못하고 있어서, 값이 없는 종목은 평균단가를 매물대 POC로
추정하고 신용 과열도가 1.25점으로 캡된다. 그 결과 매집 점수 상한이 8.49점이다.

`data/credit_manual.csv`에 값을 넣은 종목만 실측으로 채점된다.

```
종목코드,신용잔고율,신용잔고주식수,기준일,비고
329180,4.85,,2026-08-22,김차장 제공
086520,6.20,,2026-08-22,신용 과열
```

```bash
copy data\credit_manual.csv.example data\credit_manual.csv
python run_screen.py --mode credit
```

실측이 들어오면 이렇게 바뀐다.

```
credit_heat  1.25점 캡  ->  최대 4.0점 (신용잔고율 5% 이상 만점)
청산 계층 6   비활성     ->  신용잔고율 진입 대비 +1.5%p 재급증 시 전량 청산
```

전 종목을 채울 필요 없다. 관심종목 30~50개만 주 1회 넣어도 그 종목들의
판정 정확도가 크게 올라간다. 기준일이 14일 넘게 오래된 값은 자동 제외된다.
신용잔고율만 있어도 되고, 주식수만 넣으면 마스터의 상장주식수로 역산한다.

## 주의

- 신용잔고는 익영업일, 공매도 잔고는 T+2 공시다. `CreditConfig.credit_shift` /
  `short_shift` 로 지연을 반영하며, 백테스트에서 이를 빼면 승률이 실제보다
  높게 나온다.
- 종목별 신용잔고를 확보하지 못하면 `credit_heat` 항목이 1.25점으로 캡되고
  평균단가는 매물대 POC(방법 C)로 폴백한다. 동작은 하지만 정확도가 떨어진다.
- 배제 필터(관리종목·자본잠식·대규모 증자 등)는 `flag_provider` 로 주입해야
  한다. 주입하지 않으면 잡주가 상위에 올라올 수 있다.
- `backfill`은 KRX 스크래핑이므로 `--throttle` 을 너무 낮추면 차단될 수 있다.
  기본 0.35초를 권한다.
- 자기검증(①)의 표본이 최소 4주 이상 쌓이기 전에는 승률 수치를 신뢰하지 말 것.
- 네이버 금융은 마크업을 자주 바꾼다. 셀렉터 5개를 순차 시도하고 전부
  실패하면 경고만 남기고 다른 소스로 넘어간다. 로그에 `셀렉터 미매칭`이
  보이면 셀렉터를 갱신해야 한다.
- 뉴스 브리핑 시각 판단은 KST 고정이다(`store._now_kst`). 다만 `notify.py`와
  일부 렌더러는 아직 `datetime.now()` 로컬 시간을 쓴다. UTC 서버에서
  `flash` 시간창이 열리지 않으므로 배포 전에 서버 타임존을 KST로 맞추거나
  해당 부분을 KST로 교체해야 한다.

## 미완성 항목

- 종목별 신용잔고 **자동** 수집 경로가 없다. `--mode credit` 으로 수동
  주입은 가능하지만(위 참조), 넣지 않은 종목은 평균단가 P0 를 매물대 POC 로
  추정하므로 청산 밴드의 정확도가 떨어진다. KRX 정보데이터시스템 또는
  증권사 API 연동이 근본 해법이다.
- 감사의견 판정은 공시 **제목** 키워드 스캔이라 취약하다. 의견거절이 제목에
  드러나지 않는 경우가 많다. 다만 그런 종목은 대개 관리종목으로 지정되어
  ①에서 잡힌다. 확실히 하려면 `flags_manual.csv`로 직접 지정하십시오.
- `backtest.py`: 없다. 청산 파라미터(익절폭·트레일링폭·시간스톱·밴드 이탈
  확인일수)는 전부 가설이며 아직 검증되지 않았다.
- 본 코드는 스크리닝 도구이며 투자 판단을 대신하지 않는다. 실탄 투입 전
  과거 데이터 검증(승률·추가 하락폭·지수 대조군)이 반드시 필요하다.

## Hermes 자동화

호스트는 Windows PC (KST) 이고, Hermes 의 내장 cron 이 배치를 돌린다.
운영 규약은 `AGENTS.md` 에 있다. 에이전트는 그 파일을 읽는다.

### 반드시 래퍼를 통해 실행한다

```
hermes\run.cmd --mode daily --json
hermes\run.cmd smoke
hermes\run.cmd verify
```

`python run_screen.py` 직접 호출은 이 PC 에서 실패한다. 확인된 원인 셋이다.

```
python  ->  C:\...\WindowsApps\python.exe    Microsoft Store 스텁. 실행되지 않음
PATH 에 실제 인터프리터 없음                  %LOCALAPPDATA%\Programs\Python\Python312
콘솔 코드페이지 949 (cp949)                   한글 stdout 이 깨져 에이전트가 오독
```

래퍼가 인터프리터를 명시적으로 찾고, `PYTHONUTF8=1` 로 UTF-8 을 강제하고,
작업 디렉터리를 저장소 루트로 고정한다.

`hermes\run.cmd` 는 **의도적으로 ASCII 전용**이다. cmd.exe 는 배치 파일을
현재 코드페이지로 읽으므로, 비ASCII 바이트가 있는 파일에서 `chcp` 를 호출하면
파서가 동기를 잃고 주석을 명령으로 실행한다. 실제로 겪은 문제다. 한글 문서는
`AGENTS.md` 에 둔다.

### 결과는 JSON 으로 받는다

`--json` 을 붙이면 stdout 에 한 줄 JSON 이 나오고 로그는 stderr 로 분리된다.
한글 로그를 스크레이핑하지 않아도 된다.

```json
{"mode":"daily","trade_date":"2026-08-24","scanned":1847,"failed":3,
 "picks":10,"top":[{"rank":1,"ticker":"329180","name":"HD현대중공업",
 "grade":"S+","slot":"SEQ","value":8.7,"trend":8.5}],
 "exit_code":0,"elapsed_sec":214.3}
```

### 종료 코드

```
0   정상
1   실패 (예외/치명적)
2   부분 실패 (실패율 10% 초과)
3   락 충돌 — 재시도 대상
4   전제조건 미충족 (순서 오류 또는 .env 미설정)
64  인자 오류 — 재시도 무의미
90  저장소 이동 실패 (래퍼)

```

`argparse` 기본값이 2 라 부분 실패와 겹치는 문제가 있어 인자 오류만
64(EX_USAGE)로 분리했다.

### 동시 실행 방지

DB 를 쓰는 모드는 `data/locks/quant.lock` 파일 락으로 직렬화된다. SQLite 는
WAL 에서도 쓰기끼리 직렬화되므로 겹치면 `database is locked` 로 죽는다.

```
--lock-wait 300     락이 잡혀 있으면 최대 5분 대기
--force-unlock      남은 락을 강제 해제하고 시작 (남용 금지)
```

락 파일에 만료 시각이 적혀 있어 잡이 죽어도 영구 차단되지 않는다. 모드별
예상 시간을 준다 (backfill 2시간, daily 30분).

### 전원 설정

PC 가 절전/최대 절전으로 들어가면 cron 이 돌지 않는다. 전원 옵션에서 절전을
끄거나 깨우기 타이머를 허용해야 스케줄이 유지된다.

## 휴장일 처리

주말·공휴일에 배치가 돌아도 오작동하지 않는다. 실제로 여섯 개의 버그가
있던 영역이라 별도 모듈(`stocknews/trading_day.py`)로 분리했다.

### 판정 방식 — 공휴일 목록을 하드코딩하지 않는다

매년 바뀌고 임시 휴장도 있다. 세 단계로 판정한다.

```
주말            요일로 확정                    CLOSED_WEEKEND
알려진 휴장일   DB 캐시(non_trading_days)      CLOSED_HOLIDAY
시세가 있는 날  거래일 확정                    TRADING
그 외 평일      미확인                         UNKNOWN
```

`UNKNOWN` 은 차단하지 않는다. 장중에는 아직 시세가 적재되지 않았을 수
있으므로, 확실히 휴장인 경우만 막아야 한다. 이걸 반대로 하면 매일 아침
스캔이 막힌다.

'일자별 전종목' 조회가 0건이면 그 날짜를 휴장일로 기록한다. 자기 학습형이라
새 공휴일을 만나면 한 번 헛조회하고 다음부터 건너뛴다.

### 고친 버그 여섯 개

**1. `refresh_master` 가 휴일에 전 종목을 비활성화 (치명적)**

공휴일에는 종목 목록 조회가 빈 결과를 준다. 그 상태로 `mark_inactive(빈집합)`
을 호출하면 active=1 인 모든 종목이 active=0 이 되고, 이후 모든 배치가
`exit 4` 로 죽는다. 스케줄에 매일 `master` 가 있으니 **공휴일마다 시스템이
멈춘다.** 목록이 비정상적으로 적으면(500개 미만 또는 기존의 50% 미만)
갱신하지 않고 그대로 둔다. 조회 실패를 상장폐지로 오해하는 것보다 갱신을
미루는 쪽이 언제나 안전하다.

**2. 알림 시간창이 요일을 몰랐다**

`in_window()` 가 시각만 봤다. 토요일 10:00 에 창이 열려 `flash` 가 전종목을
스캔하고 금요일 데이터로 알림을 보냈다. `AlertGate(store=...)` 를 주면
휴장일 판정이 작동한다.

**3. `daily`/`exits` 가 휴장일에 중복 실행**

`last_price_date()` 가 직전 거래일을 가리키므로 토·일에 같은 거래일
스냅샷을 재생성하고 Top-10 을 3회 발송했다. 손절 신호는 매일 재발송
설계라 토·일에도 같은 알림이 갔다. 거래일 단위 중복 가드를 넣었다.

**4. 월요일 아침 브리핑이 주말 뉴스를 놓쳤다**

`hours=16` 이면 월요일 08:30 에 일요일 16:30 이후만 본다. 금요일 장 마감
이후 뉴스가 통째로 빠진다. 마지막 거래일 마감 이후를 전부 덮도록 자동
확장한다(상한 120시간).

**5. `update` 가 공휴일을 영구 재요청**

주말은 요일로 건너뛰었지만 공휴일은 매번 요청했다. 성공해도 0건이라
`existing_dates` 에 안 들어가서 catchup 기간(7일) 내내 반복됐다.

**6. 쿨다운이 달력일 기준**

`cooldown_days=5` 가 거래일 의도인데 `(today-last).days` 는 달력일이다.
금요일 발송 후 수요일이면 달력 5일이지만 거래일은 3일이다.

### 매일 걸어도 되는 이유

휴장일에는 각 모드가 스스로 생략하고 `exit 0` + `{"skipped":true}` 를
돌려준다. 실패가 아니므로 에이전트가 재시도하지 않는다.

```bash
python run_screen.py --mode daily --json
{"mode":"daily","skipped":true,"reason":"CLOSED_WEEKEND — daily 생략",
 "exit_code":0,"elapsed_sec":0.1}
```

`--force` 로 가드를 무시할 수 있지만 중복 알림이 발송되므로 스냅샷을 다시
만들어야 할 때만 쓴다.

## 백테스트

```bash
python run_screen.py --mode backtest --limit 200 --bt-step 5
python run_screen.py --mode backtest --bt-no-controls --bt-no-exits  # 빠른 확인
```

**운영 코드를 그대로 씁니다.** 백테스트용 별도 스코어링을 만들면 두 구현이
갈라지고 그때부터 결과가 무의미해집니다. `screen_one` / `evaluate_position`
을 시계열 절단해 호출합니다. 우리 지표는 전부 과거만 참조하므로 절단만으로
룩어헤드가 차단됩니다.

### 정직한 측정을 위한 네 가지

```
익일 시가 체결   종가로 판정하므로 실제 체결은 다음 날. 종가 체결로
                 계산하면 성과가 부풀려진다
왕복 비용 차감   수수료 + 거래세 0.5%
최대 역행폭(MAE) 보유 중 최저가까지의 낙폭. "얼마나 더 빠졌나"
대조군 3종       시장 중위 / 무작위 진입 / 단순 RSI<30
```

**대조군이 핵심입니다.** 시장 대비 초과수익이 없으면 그건 전략이 아니라
하락장 베타입니다. 단순 RSI<30 보다 낫지 않으면 이 복잡도를 정당화할 수
없습니다. 리포트가 이 판정을 자동으로 내리고, 경고가 있으면 `exit 2` 로
끝냅니다.

### 청산 규칙 시뮬레이션

고정 보유가 아니라 **실제 청산 엔진**으로 청산합니다. 익절폭·트레일링폭·
시간스톱·밴드 이탈 확인일수를 검증하는 유일한 방법입니다. 어느 계층이
실제로 일하는지 계층별로 집계합니다.

```
계층별 (어느 규칙이 실제로 일하는가):
  1 손절      n=  120  평균  -8.42%  승률   4%  보유  6.2일
  5 목표1차   n=   88  평균 +15.10%  승률 100%  보유 11.4일
  6 시간      n=  201  평균  +0.31%  승률  48%  보유 15.0일
```

### 임계값 스윕

이벤트를 한 번 만들어두면 점수 임계값은 사후 필터링으로 공짜로 스윕됩니다.
재계산이 필요 없습니다.

## 신용잔고 자동 수집

```bash
python run_screen.py --mode credit-probe    # bld 코드 탐침 (최초 1회)
python run_screen.py --mode credit          # KRX 자동 + 수동 CSV 덮어쓰기
python run_screen.py --mode credit --no-krx # 수동 CSV 만
```

KRX 정보데이터시스템의 통계 조회는 `getJsonData.cmd` 엔드포인트에 `bld`
파라미터로 접근합니다. 다만 **'신용거래융자 종목별 잔고'의 정확한 bld 코드는
확인되지 않았습니다.** 추측을 코드에 박으면 조용히 빈 결과가 나오고 그걸
'신용잔고 0'으로 오해하게 됩니다. 그래서 탐침 도구를 함께 넣었습니다.

`credit-probe` 가 후보를 시험하고 어느 코드가 어떤 컬럼을 주는지 보고합니다.
전부 실패하면 직접 찾는 절차를 안내합니다.

```
1. https://data.krx.co.kr 접속
2. [통계] > [주식] 에서 신용융자 잔고 화면을 연다
3. F12 > Network 탭 > 조회 버튼 클릭
4. getJsonData.cmd 요청의 Payload 에서 bld 값 복사
5. --mode credit-probe --bld <복사한값> 으로 재확인
6. .env 에 KRX_CREDIT_BLD= 로 고정
```

응답 컬럼명도 하드코딩하지 않고 패턴으로 탐색합니다. KRX 는 컬럼명을 자주
바꿉니다. 확정 전까지는 `data/credit_manual.csv` 수동 주입이 그대로 유효하고,
수동 값이 항상 자동 수집을 덮어씁니다.
